Introduction

Mira is push notification infrastructure for web, Android and iOS. Your backend sends one JSON request and Mira handles provider integrations, queues, retries, quota reservations, delivery records and signed webhooks.

  • Transport. HTTPS with JSON request and response bodies. UTF-8 only.
  • Authentication. A project-scoped bearer key on every request.
  • Idempotency. Optional Idempotency-Key header on writes.
  • Traceability. Every response carries a request_id; support can trace it end to end.

Sandbox first. Test keys use the _test_ infix and never touch live provider credentials. Nothing sent with a test key can reach a real device.

Authentication

Every request includes a project key as a bearer token. Keys are environment-specific and only valid for the project that created them.

http 
Authorization: Bearer mira_sk_live_…
Content-Type: application/json
Idempotency-Key: launch-2026-11-10

Key types

PrefixWhere it livesAllowed scopes
mira_sk_live_Server only. Hashed at rest, never returned again after creation.Any scope granted at creation.
mira_sk_test_Server only. Safe for CI, staging and local development.Any scope, sandbox providers only.
mira_pk_live_Browser and mobile clients. Public by design.subscribers:write only.
mira_pk_test_Browser and mobile clients in sandbox.subscribers:write only.

A secret key is shown once at creation. Mira stores an HMAC-SHA256 hash with a server-side pepper; it cannot be recovered. Revoke and rotate from API keys.

Scopes

  • notifications:send — create and cancel notifications.
  • notifications:read — read notifications and their delivery summaries.
  • subscribers:read / subscribers:write — list and manage subscribers.
  • webhooks:manage — create, rotate and delete webhook endpoints.
  • usage:read — read quota and usage counters.

A request missing a required scope fails with 403 insufficient_scope. Publishable keys can never send notifications.

Projects & environments

A project is the isolation boundary. Subscribers, keys, notification records, delivery logs, webhook endpoints and quota all belong to exactly one project. Ownership is checked on every request; a key from one project cannot read another project's records.

  • Live and test. Each project has separate keys per environment. Test sends never touch live provider credentials.
  • Quota. The free allowance is 1,000 delivery units per day, calculated per project, resetting at 00:00 UTC.
  • Rotation. Multiple keys can be active during a rotation window. Revocation is immediate.
  • Deletion. Deleting a project revokes its keys immediately and purges delivery logs on the retention schedule.

Project switching in the dashboard is a view change only. It never reuses keys or merges records between projects.

Quickstart

Three steps from an empty project to an auditable delivery.

1. Create a project and secret key

In the dashboard, create a project and generate a secret key with the notifications:send and subscribers:write scopes. Copy the key once, then store it in your server environment:

.env 
MIRA_SECRET=mira_sk_live_…
MIRA_PUBLISHABLE=mira_pk_live_…

2. Register a subscriber

Browser clients obtain a PushSubscription from the service worker and send it to your backend. Register it with Mira using the publishable key, or proxy the call through your server.

curl 
curl -X POST https://api.lazytown.dev/v1/subscribers \
  -H "Authorization: Bearer mira_sk_live_…" \
  -H "Content-Type: application/json" \
  -d '{
    "external_id": "user_812",
    "platform": "web",
    "web": {
      "endpoint": "https://fcm.googleapis.com/fcm/send/…",
      "keys": { "p256dh": "…", "auth": "…" }
    },
    "locale": "en-GB",
    "tags": { "plan": "growth" }
  }'

3. Send a notification

Target everyone, a saved segment or specific subscriber IDs. The request returns 202 Accepted once quota is reserved and jobs are queued — not when a device displays it.

curl 
curl -X POST https://api.lazytown.dev/v1/notifications \
  -H "Authorization: Bearer mira_sk_live_…" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: launch-2026-11-10" \
  -d '{
    "title": "New dashboard is live",
    "body": "Charts and delivery logs are here.",
    "url": "https://acme.dev/changelog",
    "target": { "type": "segment", "id": "seg_active_web" }
  }'

// 202 Accepted
{
  "id": "ntf_01JCH4K9X2",
  "status": "queued",
  "reserved_units": 840,
  "request_id": "req_8f31c2"
}

Track the fan-out in delivery logs or subscribe to notification.completed webhooks.

Subscribers

POST /v1/subscribers registers a device or browser subscription. Creating with an existing external_id and platform updates that subscriber instead of duplicating it.

FieldTypeNotes

web.endpointstringWeb Push endpoint URL from the PushSubscription.
web.keys.p256dhstringBase64url public key from the subscription.
web.keys.authstringBase64url auth secret from the subscription.

localestringBCP 47 locale, e.g. en-GB.

Browser registration

Serve your service worker, request permission from a user gesture, then forward the subscription to your backend. Never expose a secret key in client code.

javascript 
const registration = await navigator.serviceWorker.register('/sw.js');
const permission = await Notification.requestPermission();
if (permission !== 'granted') throw new Error('Permission denied');

const subscription = await registration.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: '<VAPID public key>',
});

await fetch('/api/push/subscribe', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(subscription),
});

List, update and remove

  • GET /v1/subscribers — cursor paginated, filter by platform, tag or status.
  • PATCH /v1/subscribers/{id} — update tags, locale or metadata.
  • DELETE /v1/subscribers/{id} — mark unsubscribed and stop sending immediately.

Tokens rejected as permanently invalid (for example FCM UNREGISTERED or APNs BadDeviceToken) are marked expired and stop consuming quota on later sends.

Notifications

POST /v1/notifications creates a notification and fans it out asynchronously. The response is 202 after validation, quota reservation and queueing.

FieldTypeNotes
titlestringRequired. 1–120 characters.
bodystringRequired. 1–500 characters.
urlstringAbsolute HTTPS URL opened on click.
iconstringAbsolute HTTPS image URL, at least 192×192.
targetobjectall, segment or subscribers.
dataobjectCustom payload available in the service worker. Max 4 KB.
schedule_atISO 8601Optional future UTC timestamp. Max 30 days ahead.

Targeting

  • { "type": "all" } — every active subscriber in the project.
  • { "type": "segment", "id": "seg_active_web" } — a saved segment evaluated at send time.
  • { "type": "subscribers", "ids": ["sub_9f2c", "sub_4a81"] } — explicit subscriber IDs, max 1,000 per request.

Idempotency

Send an Idempotency-Key header on creation. Repeating the same key with the same body returns the original response and never creates a duplicate send. Reusing a key with a different body returns 409 idempotency_conflict. Keys are retained for 24 hours.

Cancellation

POST /v1/notifications/{id}/cancel cancels any jobs that have not started processing. Already accepted deliveries cannot be recalled; the response reports how many jobs were cancelled.

Delivery statuses

Status applies per notification and per delivery record. Only the four terminal states leave the pipeline; everything else is still in progress.

StatusMeaningTerminal
PendingRecord created, awaiting validation and quota reservation.No
QueuedQuota reserved and the job is waiting on a provider worker.No
ProcessingA worker is calling the provider. Retries return here.No
AcceptedThe provider accepted the message for delivery.Yes
FailedPermanent error or attempts exhausted. Provider error is recorded.Yes
ExpiredSubscription expired, token unregistered or provider TTL elapsed.Yes

Accepted is not displayed. Acceptance means the provider queued the message. Browsers, Android and iOS do not reliably confirm display, so Mira never reports “delivered” or “seen” unless a provider explicitly exposes that event.

pending → queued → processing → accepted | failed | expired

Retries move a record back to processing without creating a new delivery record or charging quota again.

Filter by notification, subscriber, platform, status or an ISO 8601 from/to range. The dashboard uses the same endpoint as the export.

Errors

Errors use a single JSON envelope. Always branch on error.code, not the human-readable message.

json 
{
  "error": {
    "code": "quota_exceeded",
    "message": "Daily delivery quota exhausted for this project.",
    "details": {
      "limit": 1000,
      "used": 988,
      "requested": 128,
      "resets_at": "2026-11-11T00:00:00Z"
    }
  },
  "request_id": "req_8f31c2"
}
HTTPCodeWhat to do
400validation_errorRead details.fields; do not retry unchanged.
401invalid_keyCheck the bearer token, environment and project.
403insufficient_scopeAdd the required scope to a new key.
404not_foundVerify the ID belongs to the current project.
409idempotency_conflictUse a new key or replay the original body.
422invalid_targetSegment or subscriber set is empty or invalid.
429quota_exceeded / rate_limitedRespect Retry-After and resets_at.
500internal_errorRetry with backoff and quote the request ID.
503provider_unavailableMira retries automatically; safe to retry a write with the same idempotency key.

Webhooks

Webhooks deliver project events to your HTTPS endpoint. Each request is signed with HMAC-SHA256 so you can verify it originated from Mira. Configure endpoints and rotate secrets in Webhooks.

Events

  • subscriber.created / subscriber.expired
  • notification.queued / notification.accepted / notification.failed / notification.completed
  • quota.warning — sent once at 80% of the daily allowance.

Headers

http 
Mira-Event: notification.accepted
Mira-Event-Id: evt_01JCH9
Mira-Delivery: 1
Mira-Signature: t=1731234567,v1=5f2c9d…

Payload

json 
{
  "id": "evt_01JCH9",
  "type": "notification.accepted",
  "created_at": "2026-11-10T09:12:44Z",
  "project_id": "prj_acme_live",
  "data": {
    "notification_id": "ntf_01JCH4K9X2",
    "delivery_id": "dlv_01JCH5A7",
    "subscriber_id": "sub_9f2c",
    "platform": "web",
    "status": "accepted",
    "attempts": 1
  }
}

Verify the signature

Compute HMAC-SHA256 over the string timestamp + "." + rawBody using your endpoint secret. Compare in constant time, reject timestamps older than five minutes and deduplicate on Mira-Event-Id. Respond with any 2xx within 5 seconds.

HMAC-SHA256 
$raw = file_get_contents('php://input');
$header = $_SERVER['HTTP_MIRA_SIGNATURE'];
parse_str(str_replace(',', '&', $header), $parts);

$expected = hash_hmac('sha256', $parts['t'] . '.' . $raw, config('services.mira.webhook_secret'));

if (!hash_equals($expected, $parts['v1'])) {
    abort(403, 'Invalid signature');
}

$event = json_decode($raw, true); // after verification
const crypto = require('node:crypto');

const raw = req.rawBody; // Buffer, before JSON.parse
const signature = req.get('Mira-Signature');
const parts = Object.fromEntries(signature.split(',').map((p) => p.split('=')));
const expected = crypto
  .createHmac('sha256', process.env.MIRA_WEBHOOK_SECRET)
  .update(parts.t + '.' + raw)
  .digest('hex');

if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1))) {
  return res.status(403).send('Invalid signature');
}

Retries

Non-2xx responses, timeouts over 5 seconds and connection errors are retried on a dedicated queue with exponential backoff. Endpoints returning repeated failures are flagged in the dashboard but stay active until you disable or delete them.

Quotas & rate limits

Free projects receive 1,000 delivery units per day, per project, resetting at 00:00 UTC. One notification to one subscriber consumes one unit; sending to 100 devices reserves 100 units.

Reservation rules

  • Units are reserved atomically inside a transaction before any job is queued. Concurrent requests cannot overspend the allowance.
  • Retries and provider failover reuse the original reservation and never charge twice.
  • Units for targets that are never handed to a provider are returned to the daily balance.
  • Invalid tokens marked expired do not consume future quota.

Rate limits

Requests are limited per key. When a limit is exceeded the response is 429 rate_limited with:

response headers 
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1731234600
Retry-After: 30

Read remaining quota at GET /v1/usage. Subscribe to quota.warning to be notified at 80% of the daily allowance.

Pagination

List endpoints use cursor pagination. Pass limit (1–100, default 25) and the starting_after cursor from the previous response.

json 
{
  "data": [ /* … */ ],
  "has_more": true,
  "next_cursor": "cur_01JCH7Q2"
}

Treat cursors as opaque strings. Totals are approximate and only returned for small collections; never paginate by page number.

Versioning

The API version is part of the URL (/v1). Additive changes — new fields, new enum values, new optional parameters — may ship without a version bump. Clients must ignore unknown fields and handle unknown enum values gracefully.

Breaking changes ship under a new path version with at least 12 months of overlap. Deprecated endpoints return a Deprecation header and a Sunset date.

Need help? Include the request_id from any failing response when contacting support.
